1. О программе
Плагин внутреннего просмотра uLister поддерживает более 500 различных форматов файлов.

2. Поддерживаемые форматы
Множество популярных форматов текстовых процессоров, электронных таблиц, презентаций, растровых и векторных изображений.
Полный список можно посмотреть в файле OutsideIn_8.5.7_Supported_File_Formats.pdf

5. Настройка
Параметры хранятся в файле ulister.ini, поиск которого производится в следующем порядке:
1) каталог плагина 
2) каталог, в котором находится %COMMANDER_INI% 
3) %APPDATA% 
Файл не будет загружен, если длина пути превысит 260 символов (ограничение Windows).

С версии 4.2.0.0 если файл ulister.ini так и не найден, плагин попытается создать файл с дефолтными настройками в своем каталоге.

Имя секции настроек - [ulister].

В версии 4.0.0.4 плагина доступны следующие параметры:

keepinmemory        (по умолчанию 1) - не выгружать библиотеки Outside In Viewer из памяти после первого использования, что уменьшает
                    время загрузки документа, но увеличивает потребляемую память.
noloadtypes         список запрещенных к загрузке форматов
onlyloadtypes       список разрешенных к загрузке форматов
nopreviewtypes      список запрещенных к показу эскизов форматов
onlypreviewtypes    список разрешенных к показу эскизов форматов

Четырехзначные коды форматов с описанием находятся в файле formats.txt (см. также сочетание клавиш Ctrl+I).
В качестве разделителя можно использовать любой символ, отличный от цифр, например, запятую или пробел.
Если задана разрешающая строка, то аналогичная запрещающая строка игнорируется.

optionsdir          путь к каталогу, в котором создается подкаталог ".oit" с внутренними настройками библиотеки Oracle Outside In Technology: Viewer Technology;
                    поддерживаются %переменные% окружения;
                    ограничение Windows - длина пути не более 260 символов;
                    для коректной работы optionsdir необходимо использовать пропатченную версию файла sccut.dll,
                    некоторые исправленные версии этого файла лежат в каталоге "OIT_DATA_PATH support" (например, последние, поддерживающие Windows XP)

Если параметр optionsdir не указан, то библиотека создает ".oit" в %APPDATA%, если это значение не определено, то в %LOCALAPPDATA%,
если это значение тоже не определено, то в каталоге с библиотекой.

mwhscrollinvert     (по умолчанию on) - инвертировать горизонтальную прокрутку колесиком мыши
                    off - не инвертировать. опция доступна начиная с версии 4.0.3.0

В версии 4.2.0.0 появилось отображение всплывающих подсказок при переключении режимов:

tooltipsdelayms     (по умолчанию 3000) - время показа подсказки в миллисекундах
tooltipstransparency (по умолчанию 244, от 0 до 255 включительно) - прозрачность подсказки (работает только в Windows 8 и выше, не нагружая более старые системы);
                    используйти значение -1, чтобы принудительно отключить режим прозрачности.

С версии 4.0.0.7 плагина с помощью ulister.ini можно изменять некоторые полезные (и не очень) внутренние настройки библиотеки Outside In Technology, хранящиеся в
проприетарном бинарном представлении в каталоге ".oit".

Практически все такие опции по умолчанию имеют специальное зарезервированное значение skip, т.е. "пропустить" эту настройку из ini-файла и взять
внутреннюю настройку библиотеки, хранящуюся в Outside In Technology (каталог ".oit").
Однако если в ini настройка явно задана другим значением, то библиотека (не плагин) перезаписывает это значение в .oit.

Первая часть этих параметров связана с настройкой копирования библиотеки Outside In Technology в буфер обмена, а опции должны находиться в секции clipboard.
Некоторые настройки можно изменить из контекстного меню. Кому-то захочется, чтобы эти настройки запоминались,
для этого в ini-файле они должны задаваться как skip. А кому-то захочется, чтобы эти настройки можно было приводить в
первоначальное состояние из ini-файла перезапуском Total Commander, чтобы их нельзя было сломать из меню - тогда
в ini-файле они задаются явно. Впрочем, большинство других настроек отсутствуют в контекстном меню, и их можно менять только из ini-файла.

Основная группа - это то, что можно увидеть с помощью вызова контекстного меню на открытом документе Options->Clipboard.
Они определяют, в каком формате разрешено помещать блок в буфер обмена (SDK раздел A.10.10 SCCID_TOCLIPBOARD).

[clipboard]
; This option controls the clipboard formats that the viewer attempts to place on the clipboard
ascii=skip|on|off
rtf=skip|on|off
unicode=skip|on|off (по умолчанию этот параметр выключен, что в оригинале приводило к появлению "крякозябр" при копировании национальных символов)
bitmap=skip|on|off
windib=skip|on|off
metafile=skip|on|off
palette=skip|on|off

Следующая настройка разрешает или запрещает копирование с помощью перетаскивания выделенного блока (drag-and-drop) (SDK раздел A.10.6 SCCID_OLEFLAGS).
dragdrop=skip|on|off
Этой настройкой также можно управлять из контекстного меню "Options->Drag'n'Drop" (версия плагина 4.4.0.0)

Рекомендуется установить "on" для всех параметров секции clipboard (особенно для unicode).

Настройка задает формат копирования ячеек из электронных таблиц (SDK раздел A.4.8 SCCID_SSCLIPBOARD)
или из баз данных (SDK раздел A.4.1 SCCID_DBCLIPBOARD)
spreadsheet=skip|rtf|tabs|optimizedtabs
database=skip|rtf|tabs|optimizedtabs
    rtf         - копирование как таблицы в формате rtf
    tabs        - как обычный текст, разделенный между ячейками символом табуляции
    optimizedtabs - как в предыдущем случае, но пустые ячейки пропускаются

В версии 4.0.1.0 плагина доступны настройки для изменения отображения документов текстового процессора, HTML и EMAIL в секции viewer
(SDK раздел A.7.2 SCCID_WPDISPLAYMODE / SCCID_HTMLDISPLAYMODE / SCCID_EMAILDISPLAYMODE)
[viewer]
wpdisplaymode=skip|draft|normal|preview|weblayout
htmldisplaymode=skip|draft|normal|preview|weblayout
emaildisplaymode=skip|draft|normal|preview|weblayout
    draft       - черновое отображение документа одним шрифтом одинакового размера без графики, без границ таблиц и т.п.
    normal      - использовать форматирование, но текст подгоняется под размер окна
    preview     - использовать форматирование, текст размещается на странице как при печати
    weblayout   - использовать форматирование, текст размещается как на странице браузера

Управление размером страницы в режимах preview и weblayout для класса форматов Word/HTML/EMAIL
(SDK раздел A.7.3 SCCID_WPFITMODE / SCCID_HTMLFITMODE / SCCID_EMAILFITMODE)
Эти настройки корректно применяются только после второго запуска ulister после внесения изменений
в файл .ini (workaround) из-за ошибки в библиотеке Outside In Viewer.

webprevwpfitmode=skip|original|width|window
webprevhtmlfitmode=skip|original|width|window
webprevemailfitmode=skip|original|width|window
    original    - задает актуальный размер страницы в режиме preview
    width       - размер страницы по ширине окна в режиме preview
    window      - вписать страницу в окно в режиме preview; в режиме weblayout по ширине окна.

В версии 4.0.2.0 плагина доступны настройки для управления отображением растровой и векторной графики
(SDK разделы A.5.11 SCCID_VECFITMODE, A.5.4 SCCID_BMPFITMODE)
Некоторые контейнеры изображений, такие как Macintosh Pict, могут содержать как растровую, так и векторную графику.
Библиотека Outside In Technology почему-то относит такие файлы к векторным.
vectorfitmode=skip|best|original|window|height|width|stretch
bitmapfitmode=skip|best|original|window|height|width|stretch***|imagesize
    best        - Если размер окна просмотра меньше размера исходного изображения, эта опция подгонит изображение под размер окна.
                Если размер окна просмотра больше размера исходного изображения, изображение будет отображаться в исходном размере.
    original    - Изображение отображается на экране по одному пикселу на каждую единицу в системе координат изображения для векторного представления
                или пиксел в пиксел для растрового; размер окна не имеет значения.
    window      - Изображение будет растянуто, чтобы заполнить как можно большую часть окна, сохраняя при этом правильное соотношение сторон.
    height      - Изображение будет растянуто так, чтобы его полная высота соответствовала высоте окна.
                В зависимости от изображения, его полная ширина может поместиться внутри окна, а может и нет.
    width       - Изображение будет растянуто так, чтобы его полная ширина поместилась в ширину окна.
                В зависимости от изображения, его полная высота может поместиться в окно или нет.
    stretch     - Изображение будет растянуто, чтобы заполнить окно. Соотношение сторон изображения НЕ сохраняется.
                Хотя параметр stretch определен в SDK для растровой графики, однако для нее он не имеет никакого эффекта.
    imagesize   - Масштабировать до размера изображения.

В версии 4.1.0.0 плагина доступна настройка для управления отображением электронных таблиц
(SDK разделы A.4.9 SCCID_SSDRAFTMODE, A.4.19 SCCID_SSSHOWHIDDENCELLS)
spreadsheetdisplaymode=skip|draft|normal|normalhidden
    draft       - черновое представление документа одним шрифтом одинакового размера без графики и т.п.
    normal      - отображение без ограничений
    normalhidden- дополнительно отображать скрытые строки и столбцы

В версии 4.4.0.0 плагина в секции memory доступны следующие настройки управления памятью:

[memory]
readbuffersizekb=skip|Size_KB
mmapbuffersizekb=skip|Size_KB
tempbuffersizekb=skip|Size_KB
memorymode=skip|4m|16m|64m|256m|1024m

(SDK раздел A.12.1 SCCID_IO_BUFFERSIZE)

Значение указывается в килобайтах, с помощью префикса "0x" можно задавать значения в шестнадцатеричном формате
(или с "0" в восьмеричном, если вы работаете на PDP-11, поэтому лучше никогда не пишите здесь числа, начинающиеся с нуля, такие как "012"!).

ReadBufferSizeKB используется для определения количества килобайт, которые будут считываться с диска в память за раз.
Как только буфер наполнится данными, дальнейшее чтение файла будет продолжаться внутри буфера до достижения его конца,
после чего буфер снова заполняется с диска. Это может привести к повышению производительности во многих форматах файлов,
независимо от размера документа.

Значение по умолчанию - 2 КБ,
минимальное значение - читать по 1 КБ за раз, максимальное - 4194303 (4 ГБ минус 1 КБ или 0x003fffff)

MMapBufferSizeKB используется для определения максимального размера документа и применения модели ввода-вывода с отображением в память (memory-mapped I/O).
В этом случае весь файл считывается с диска в память, а все дальнейшие операции ввода-вывода выполняются над данными в памяти.
Это может значительно повысить производительность, но следует отметить, что либо весь файл может быть считан в память, либо нет.
Если одновременно заданы ReadBufferSizeKB и MMapBufferSizeKB, то если размер файла меньше MMapBufferSizeKB, весь файл будет считан в память;
иначе он будет считан блоками, определенными параметром ReadBufferSizeKB.

Значение по умолчанию - 8192 КБ (отображение в память файлов до 8 МБ),
минимальное значение - 0 КБ (не использовать ввод-вывод с отображением в память), максимальное - 4194303 (4 ГБ минус 1 КБ или 0x003fffff)

TempBufferSizeKB - это максимальный размер, который временный файл может занимать в памяти до записи на диск в виде физического файла.
Хранение временных файлов в памяти может повысить производительность при работе с архивами и файлами,
содержащими встроенные объекты или вложения.

Значение по умолчанию - 2048 КБ (временный файл в памяти ограничен 2 МБ),
минимальное значение - 0 КБ (любые временные файлы сразу пишутся на диск), максимальное - 4194303 (4 ГБ минус 1 КБ или 0x003fffff)
(замечание от evgen_b - скорее всего здесь имеется ввиду общий размер сразу для всех необходимых временных файлов, а не одного)

(SDK раздел A.12.3 SCCOPT_DOCUMENTMEMORYMODE)

Параметр MemoryMode определяет максимальный объем памяти, который модуль обработки данных может использовать для хранения данных документа,
от 4 МБ до 1 ГБ. Чем больше памяти доступно модулю обработки данных, тем реже ему требуется повторно считывать данные из документа.
Значение по умолчанию - 256 МБ.

6. Установка
Библиотеку Oracle Outside In Technology: Viewer Technology можно загрузить на странице
https://www.oracle.com/middleware/technologies/outside-in-technology-downloads.html

Установите плагин uLister.

Загрузите oit-8.5.8.204-vw-win-x64.zip для 64-разрядной версии TC и oit-8.5.7.243-vw-win-x32.zip для 32-разрядной версии. Распакуйте файлы.
(Если нужна поддержка Windows XP x64 SP2 или Windows XP x86 SP3, то используйте более старые версии oit-8.5.5.12-vw-win-x86-64.zip и oit-8.5.5.12-vw-win-x86-32.zip)

Если вы распаковали 64-битную библиотеку, то 64-разрядные файлы из распакованного каталога redist скопируйте в каталог redist64 плагина.
Если вы распаковали 32-битную библиотеку, то 32-разрядные файлы из распакованного каталога redist скопируйте в каталог redist32 плагина.

Если вы планируете использовать параметр optionsdir плагина, то замените файл sccut.dll соответствующей исправленной версией из каталога "OIT_DATA_PATH support".

Для работы Oracle Outside In Technology: Viewer Technology нужны актуальные версии библиотек Visual C++ Redistributables,
AIO можно установить, например, отсюдыва https://github.com/abbodi1406/vcredist

Начиная с версии 4.0.0.6 uLister выбирает библиотеки еще более гибко:
Теперь только для ОС ниже Windows 7 добавлен поиск библиотек Outside In сначала в каталогах XPdist32 или XPdist64 (более высокий приоритет),
а если ничего не нашлось, то потом как обычно - в redist32 или redist64 (более низкий приоритет). Для ОС Windows 7 и выше поиск осуществляется как и раньше,
только в redist32 или redist64. Это сделано для того, чтобы uLister мог гибко выбирать подходящие библиотеки Outside In в зависимости
от ОС, в которой он работает (устаревшие библиотеки, но с поддержкой XP/Vista и самые новые библиотеки для остальных ОС начиная с Windows 7 и выше).
Таким образом, если автоматическая поддержка XP/Vista с помощью более старых версий библиотек не нужна, то каталоги XPdist32 и XPdist64 со
старыми версиями библиотек также не нужны, и без них все будет работать как и раньше в любых ОС.

7. Сочетания клавиш
Ввод строки для поиска - Ctrl+F/F7
В версии 4.4.0.0 поиск также можно вызвать из контекстного меню с помошью правой клавишы мыши.
Поиск назад/вперед (SEARCHFORWARD/SEARCHBACK) - F3/Shift+F3
(поиск доступен не во всех форматах; поддерживается опция регистро-независимого поиска)
Можно увеличивать или уменьшать масштаб - Ctrl "+" / Ctrl "-" или Ctrl + колесо мыши (в старых версиях OutsideIn, как для WinXP, доступно не во всех режимах просмотра).
Клавиши Ctrl+NUM*/Ctrl+8 или Ctrl + средняя кнопка мыши - сбросить масштаб на 100%.
Используйте Shift + колесо мыши (или отдельное горизонтальное колесо мыши) для горизонтальной прокрутки.

*** Для не-графических документов изменение масштаба реализуется только с помощью изменения размера шрифта, в определенных ситуациях это
приведет к некоторому сбою форматирования документа, однако это все же лучше, чем совсем ничего.
В библиотеке Outside In Technology так и не было реализовано полноценное масштабирование для не-графических документов, похоже, интерфейс сообщений от мыши для
масштабирования и горизонтальной прокрутки, напротив, был специально программно затруднен в этой библиотеке из-за артефактов визуализации.

В некоторых форматах можно выделить блок и скопировать его в буфер обмена, либо перетащить его мышкой.
Для форматов Visio, баз данных и электронных таблиц можно переключаться между листами с помощью Ctrl+PgDn/Ctrl+PgUp.
Для презентаций PowerPoint/Lotus Freelance и т.п. переключение слайдов осуществляется клавишами PgDn/PgUp, курсорными клавишами или колесом мыши.
Таким образом, клавиши в основном обрабатываются внутри библиотеки и сильно зависят от типа документа и режима просмотра.

Outside In Viewer может работать с простыми контейнерами, такими как ZIP-файлы, MS CAB-файлы с компрессией MSZIP,

* Описание в динамике.

WLX-файл загружается тогда, когда вы в первый раз открываете в Lister ЛЮБОЙ файл и выгружается только при закрытии TC.

Для просмотра используются 3 функции, работа которых рассматривается ниже (W в конце означают UTF16-версию, как в WINAPI).

Функция ListLoadW получает имя файла, а также дескриптор существующего подготовленного TC окна-родителя,
создает в нем дочернее окно просмотра, помещает туда изображение файла и возвращает дескриптор созданного дочернего окна.

Функция ListCloseWindow (дурацкое название вводящее в заблуждение - обязательно см. подробнее ниже!) получает дескриптор
существующего дочернего окна, уничтожает его и освобождает занятые ресурсы.

Функция ListLoadNextW получает дескриптор дочернего окна (и на всякий случай окна-родителя) и имя файла
и меняет(!) в существуюущем дочернем(!) окне изображение текущего файла на полученного.

Если функция ListLoadW отработала без ошибки и возвратила HWND (не NULL), то для окна просмотра по завершении
всегда будет парный вызвов ListCloseWindow (HWND).

Именно возвращенный из ListLoadW дескриптор TC будет подсовывать оставшимся двум функциям при вызове
(чтобы плагин мог одновременно показывать несколько документов и однозначно идентифицировать связанные с ними окна просмотра).

Если функция ListLoadW возвращает ошибку (NULL), то внутри нее нужно освободить все занятые в ходе
неудачной инициализации окна ресурсы - никаких других вызовов в этом случае уже не будет (т.к. нет уникального HWND).

Любой просмотр, даже если выделено несколько файлов для разных плагинов (Shift+F3) или это быстрый просмотр (Qtrl+Q),
всегда начинается с ListLoadW (чтобы, как минимум, инициировать дочернее окно и получить его HWND).

* Множественный просмотр нескольких выделенных на панели файлов (Shift+F3) или быстрый просмотр (Qtrl+Q).

При переключении в режиме множественного просмотра (он запускается выделением нескольких файлов и нажатием Shift+F3)
на следующий/предыдущий файл (клавишами N -next и P - previous) или в режиме быстрого просмотра - курсорными клавишами из
уже загруженного функцией ListLoadW (или ListLoadNextW) документа, TC вызывает функцию ListLoadNextW в том случае,
если этот тип файла подходит под настройки фильтрации в секции [ListerPlugins] файла конфигурации Wincmd.ini (цепочка
detect-строк ***). Если в цепочке detect-строк TC не находит подходящее совпадение для текущего плагина просмотра,
то он вызывает ListCloseWindow, чтобы попробовать открыть новый файл в другом более подходящем плагине, основываясь на
анализе detect-строк.

*** Это в теории. А на практике в TC какой-то баг, и, похоже, что детект для ListLoadNextW начинается не с самой 1й detect-строки,
а происходит  только в пределах detect-строки текущего плагина (что в общем случае будет работать по-разному при одиночном или при множественном просмотре).
Для функции ListLoadW действительно поиск осуществляется по всей цепочке detect-строк начиная с первой. На практике это разделение приводит к
разным результатам выбора подходящего плагина при одинарном и множественном просмотре файлов (или при быстром просмотре). Хотя и это
не точно, потому что при просмотре картинки TC правильно переключается из ulister в Imagine, хотя должен был бы оставаться как есть.
Но для файлов HTML TC не переключается при множественном просмотре из ulister в  HTMLView. А, может это
из-за того, что у HTMLView нет UTF16-функций TC её понижает в приоритете, и при множественно просмотре HTML-файлы воспроизводятся в uLister,
а не переключают TC на использование плагина HTMLView, который задан с бОльшим приоритетом в цепочке detect-строк???

В отличие от ListLoadW, в момент вызова ListLoadNextW дочернее окно уже существует (благодаря самому первому
вызову ListLoadW) и отображает документ, поэтому (по задумке Гислера) функция никогда не должна ни создавать,
ни уничтожать существуюущее дочернее окно, более того - даже в случае возникновения ошибки! Её цель - поместить
новый файл в уже созданное когда-то ранее дочернее окно, в котором в данный момент все еще выводится этим же
плагином предыдущий файл (соответственно, ей предварительно нужно освободить занятые его изображением ресурсы).

Инициализацию дочернего окна за ListLoadNextW уже сделал первый вызов функции ListLoadW, а в случае ошибки,
когда ListLoadNextW возвращает значение LISTPLUGIN_ERROR, ТС вызывает следом функцию ListCloseWindow.

Если новый файл обработан плагином успешно, ListLoadNextW возвращает LISTPLUGIN_OK.

Только ListLoadW возвращает TC тип данных дескриптор, ListLoadNextW может только его принять в виде аргумента, поэтому
не имеет права делать его недействительным (уничтожая окно), чтобы не нарушить логику работы как плагина, так и TC в целом.

* Подробнее о функции ListCloseWindow, которая совсем не та, за кого себя выдает.

Название функции ListCloseWindow весьма неуместное и унаследовано, когда ListLoadNextW еще не существовала в API TC,
и функция действительно закрывала родительское окно. Сейчас вызов ListCloseWindow не обязательно означает, что родительское
окно будет закрыто. Правильнее считать, что она называется "ListUnload" и только удаляет с родительского окна дочернее
с изображением документа. И не важно для чего - возможно TC действительно собирается закрыть окно просмотра,
а возможно этот вызов должен вернуть "чистую" область для просмотра следующего/предыдущего файла другим плагином
в этом же родительском окне. Третий вариант - пользователь через меню переключает плагин просмотра для данного
файла, и в этом случае родительское окно тоже остается открытым. То, что после вызова ListCloseWindow родительское окно
фактически, в общем случае, на самом деле будет оставаться открытым необходимо знать, если, например, ранее плагин устанавливал хук,
процедуру субклассирования (SetWindowSubclass) или явно добавлял свою обработку оконной функции (SetWindowLongPtr) для
родительского окна - в этом случае внутри ListCloseWindow необходимо вернуть оригинальный адрес оконной процедуры
родительскому окну. В противном случае, поскольку это окно может далее использоваться уже другим плагином, то оконная процедура
родительского окна при работе в совершенно другом плагине вызовет внедренный обработчик от нашего плагина,
что, вероятнее всего, приведет к падению всего TC.

* Общие выводы

Таким образом, в любом случае только для ListLoadW фактически всегда происходит парный вызов ListCloseWindow,
а ListLoadNextW вызывается только чтобы попробовать показать другой файл в уже существующем дочернем окне и ничего более.
Создание и инициализация дочернего окна может происходить только в ListLoadW, а уничтожение -
только в ListCloseWindow. В ListLoadNextW, как правило, освобождаются только ресурсы, связанные с отображением
старого файла и назначаются новые ресурсы для отображения вместо него нового файла. У функции ListCloseWindow
неподходящее старое название, вводящее в заблуждение - совершенно не обязательно, что родительское окно будет закрыто
после ее вызова, считайте, что ее название на самом деле - "ListUnload".

ListLoadNextW был придуман для того, чтобы окно просмотра не моргало каждый раз при переключении на новый файл (если плагин 
поддерживает тип такого файла), т.е. чтобы внутри плагина лишний раз не вызывались функции создания и уничтожения дочернего окна.

Если по каким-то архитектурным причинам плагин категорически не способен в дочернем окне вместо старого документа
отобразить новый без удаления и создания заново этого дочернего окна, то ListLoadNextW реализовывать вообще не нужно.
(Однако ведь можно создавать два вложенных одно в другое дочерних окна для такого случая.)

А теперь более кратко все это можно записать следующим образом (где квадратные скобки означают необязательные вызовы):
ListLoadW(file1) -> [ ListLoadNextW(file2) -> [ ListLoadNextW(file3) -> ... [ -> ListLoadNextW(fileN) -> ]]] -> ListCloseWindow
Также напомню, что в случае ошибки в ListLoadW больше ничего не вызывается,
а возвращение ошибки из ListLoadNextW автоматически вызывает ListCloseWindow,
а ListCloseWindow на самом деле "ListUnload", и TC не обязан ничего закрывать.

Когда ListLoadW или ListLoadNextW возвращают ошибку, для TC это всего лишь значит, что плагин не поддерживают
данный тип файла, и нужно переключиться на следующий в списке плагин (в случае ListLoadNextW предварительно вызвав ListCloseWindow).

--(++8--)++ Все, что вы хотели знать о внутренних вызовах поиска, но боялись спросить.

Функция ListSearchTextW никогда не вызывается с параметром SearchStringW=L"\0" (т.е. пустой строкой поиска).

TC не хранит SearchStringW для каждого окна отдельно, этот параметр глобальный. Таким образом, одно окно TC
может менять SearchStringW в другом окне TC. Чтобы у каждого окна была своя независимая строка поиска, плагину необходимо
хранить собственную строку поиска для каждого окна. Например, копию "WindSearchStrW" нужно обновлять из SearchStringW
только при lcs_findfirst (шаг 1). При вызове find next или find previous нельзя полагаться на SearchStringW,
а вместо этого нужно использовать собственную копию "WindSearchStrW" (из шага 1).

Если в форме поиска TC не стоит галка "учитывать регистр", то строка передается строчными (т.е. маленькими)
буквами - да, TC изменяет заглавные (большие) буквы без разрешения!

Параметр поиска lcs_matchcase также глобальный, поэтому если в одном окне поиска его изменить, то в другие
окна при find next или find previous будет отдаваться новое значение (и, разумеется, пропадут заглавные буквы в строке поиска).
Выделяйте из аргумета SearchParameter только lcs_backwards или lcs_findfirst, используйте собственную хранимую оконную копию для остальных флагов.
Конкретно этому плагину не приходится хранить флаг lcs_matchcase для каждого окна, потому что за него это делает библиотека Viewer Technology внутри себя.
Кроме того, максимальная длина строки Viewer Technology - 80 байт, поэтому плагину в общем случае необходимо работать с обрезанной строкой.

8.1 С какого места начинать поиск подстроки в тексте?

С самого начала документа - ответите вы, и это причина, по которой появился этот раздел.

Мне периодически приходят просьбы, в конечном счете формализуя задачу, реализовать поиск следующим образом:
1. Начало поиска (после вызова окна поиска по Ctrl+F/F7) должно начинаться с самого начала документа (для "следующего" поиска есть сочетание F3 или Shift+F3).
2. После того, как подстрока не найдена, обязательно (именно в такой формулировке) начать поиск с самого начала документа.

И интуитивно такое умное поведение программы кажется наиболее удобным. Однако ни один известный мне коммерческий (и не только) комплексный софт
не реализует данный алгоритм. Поиск (хотя бы по умолчанию) должен начинаться с того места, в котором в данный момент находится курсор.

Сейчас я не буду докапываться, что, вообще-то, если поиск сразу начинается с отметкой "в обратном направлении", то его нужно запускать не с начала
документа, а, напротив, с конца. Рассмотрим простой случай, когда нужно найти строку string2, идущую за строкой string1:

start
text
string2
text
string1
text
string2 <- хочу найти string2, идущую после string1
text
end

Значит сначала нужно запустить поиск string1, после чего с нового текущего места запустить поиск string2.
Если поиск каждый раз начинается с начала, а не с текущего положения курсора, то достигнуть цели будет невозможно.
Предложение из п.1 в общем случае ломает работу.

А что же с п.2?
OK, допустим, мы запустили и нашли string1. Но при запуске поиска следующей строки ошибочно ввели вместо string2 строку strong2.
И если "strong2" нет в тексте, то умная программа продолжит поиск с начала документа (и хорошо, если не зациклится). А для нас это
означает, что маленькая ошибка (человеческий фактор) привела к тому, что весь квест нужно проходить заново - снова с поиска string1.
Если цепочка поиска длиннее, то вероятность ошибки тоже больше, как и штраф за нее. Другой вариант - мы хотим поискать разные варианты
после string1.

Именно поэтому вы сами явно указываете программе, откуда начинается поиск, с помощью курсора, а программа никогда не должна решать
этот вопрос за вас. Возможно, вам понравится использовать общеизвестные замечательные сочетания клавиш Ctrl+Home/Ctrl+End, чтобы быстро
добираться в начало или конец документа.


Тем не менее, окончательно закрывая вопрос, теперь в плагине (4.3.2.0) действительно реализован упрощенный режим поиска из п.1.
Для его активации в стандартном окне поиска TC теперь доступен новый пункт "FROM BEGINNING", также корректно работающий и при выборе обратного направлениия.
